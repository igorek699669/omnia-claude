# Omnia — интернет-магазин хангов

Магазин хангов (handpan), глюкофонов, RAV-драмов и комплектующих. На старте продаются только ханги. Владелец проекта — фронтенд-разработчик (React/TypeScript), проект соло.

## Стек (зафиксировано, не менять без обсуждения)

- **Next.js 16, App Router, TypeScript** — фронт и серверный слой (Route Handlers + Server Actions). Отдельного бэкенда (Nest) нет и не нужно.
- **Tailwind CSS v4** — токены в `@theme` в `app/globals.css`. Без CSS-in-JS.
- **Zustand** — корзина (`src/features/cart/model/store.ts`, там же выбранные для заказа позиции) и согласие на cookie (`src/shared/lib/cookie-consent.ts`). Оба с persist в localStorage. Не добавлять глобальные сторы без необходимости, но и не писать подписки на localStorage руками: если состояние надо читать в нескольких местах — это стор.
- **React Query** — используется точечно, только для клиентских мутаций с состояниями loading/error (например подтверждение телефона звонком в `AuthPage` и отправка заказа на чекауте), через `useMutation`. `QueryClientProvider` подключён в `app/(app)/layout.tsx` (`src/shared/lib/query-provider.tsx`). Не заводить под него `useQuery` для данных, которые и так read-only и тянутся в Server Components — там он не нужен.
- **React Hook Form + Zod** — формы (зависимости уже в package.json).
- **react-hot-toast** — единый канал уведомлений об успехе/ошибке пользовательских действий (добавление в корзину, подтверждение телефона звонком, выход из аккаунта). `<Toaster />` подключён в `app/(app)/layout.tsx` со стилями под тему проекта. Не дублировать тостом ошибки валидации формы (React Hook Form/Zod) — они остаются инлайн под полем, тост — только для результата сетевого действия/мутации.
- **Radix UI** — headless-примитивы для интерактивных контролов, ради клавиатурной доступности (Tab/стрелки/Escape). Обёрнуты в `src/shared/ui`: `Checkbox`, `RadioGroup`/`RadioChip`, `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent`, `Accordion`/`AccordionItem`/`AccordionTrigger`/`AccordionContent`, `Select`/`SelectTrigger`/`SelectContent`/`SelectItem`, `Dialog`/`DialogTrigger`/`DialogTitle`/`DialogClose`/`DialogContent`. Использовать их вместо самодельных чекбоксов/табов/аккордеонов/дропдаунов везде, где нужна семантика реального интерактивного контрола (не для нативных `<input>`/`<select>`, у которых уже отличная клавиатурная поддержка "из коробки", — там Radix не даёт выигрыша).
- **Better Auth, вход по телефону** — подключено раньше остального Roadmap (см. ниже), опережая порядок. Конфиг сервера — `auth.ts` в корне (бэкенд, не FSD, как и `payload/`), клиент — `src/shared/lib/auth-client.ts` (`authClient`, `useSession`, `signOut`). Плагин `phoneNumber`, но **код никуда не отправляется и покупатель его не вводит**: номер подтверждается входящим звонком покупателя на номер SMS.ru (метод `callcheck`, слайс `src/features/phone-auth`, `SMS_RU_API_ID` в `.env.local` обязателен). Почему не SMS: операторы отклоняют сообщения без регистрации буквенного отправителя — SMS.ru принимает их, а статус приходит 107 «не может быть доставлено» и деньги возвращаются. Flash call (звонок покупателю, код — последние цифры номера) операторы режут как спам с 2023 года, и SMS.ru свой `code/call` уже пометил устаревшим. Сессию всё равно выдаёт Better Auth: сервер сам проходит штатный путь «сгенерировать код → проверить код», перенося код через `takeGeneratedOtp` из `auth.ts` — подробности в комментариях там. Номер наружу всегда в E.164 (`normalizePhone` из `src/shared/lib/phone.ts`), в полях ввода — маска `PhoneInput`. `signUpOnVerification` заводит пользователя первым же успешным кодом и кладёт в обязательный для Better Auth `user.email` технический адрес `<цифры>@phone.omnia.local` — он служебный, нигде не показывается; реальная почта покупателя живёт только в заказе. Своя таблица пользователей в Postgres — при появлении Payload админы останутся в его собственной auth, не смешивать.
- **Email — только контакт по заказу.** На чекауте почта вводится вручную и НЕ подтверждается кодом (`EmailConfirmDialog` удалён сознательно, не возвращать). Единственное, для чего используется SMTP, — письмо продавцу об оплаченном заказе (`sendPaidOrderEmail`, см. Roadmap 3). Подтверждается на чекауте **телефон** — `PhoneConfirmDialog` тем же входящим звонком, что и на `/auth`; успешная проверка заодно заводит сессию, так что гость получает личный кабинет прямо в процессе оформления. Вошедшему номер подставляется из сессии и считается подтверждённым сразу.
- Подключены (см. Roadmap): **Payload CMS 3.x + PostgreSQL**, **ЮKassa**, **СДЭК API v2**, **Яндекс.Метрика**. Планируются: **next-intl**, **Motion**.

## Архитектура: Feature-Sliced Design

`app/` — ТОЛЬКО тонкий роутинг Next.js: каждый `page.tsx` — одна строка re-export из `src/pages`. Всю логику и разметку класть в `src/`:

- `src/pages/` — страницы (стандартный FSD-слой `pages`). Пустая папка `pages/` в корне проекта (рядом с `app/`, вне `src/`) — не удалять: без неё Next.js начинает сканировать `src/pages` как корень своего Pages Router и ломает сборку. Схема — по официальному гайду [FSD + Next.js](https://feature-sliced.design/ru/docs/guides/tech/with-nextjs).
- `src/widgets/` — крупные составные блоки (Header, Footer)
- `src/features/` — пользовательские сценарии (cart, позже auth-otp, select-delivery)
- `src/entities/` — доменные сущности (product; позже order, user)
- `src/shared/` — UI-кит, утилиты, API-клиенты

Правила: импорты только сверху вниз (pages → widgets → features → entities → shared). Каждый слайс экспортируется через `index.ts` (public API). Payload-конфиг, когда появится, живёт в `payload/` в корне — это бэкенд, не FSD.

Внутри `ui/` слайса-страницы: сам компонент страницы (`HomePage.tsx`, `CheckoutPage.tsx` и т.п.) лежит прямо в `ui/`, а компоненты, которые использует только эта страница (секции, шаги, локальные виджеты), — в `ui/components/`. Не складывать их в одну кучу. Если у страницы всего один файл — подпапка `components/` не нужна.

## Тестовый режим товара

У товара в Payload есть блок «Тестовый режим» с двумя чекбоксами — чтобы пройти покупку на
проде целиком, не заплатив за неё:

- `testPayment` — платёж создаётся в тестовом магазине ЮKassa (`YOOKASSA_TEST_SHOP_ID`/
  `YOOKASSA_TEST_SECRET_KEY`), а не в боевом. Не заданы — заказ с таким товаром не оформится:
  на боевые ключи не откатываемся, списать реальные деньги «в тесте» хуже, чем не оформить.
- `freeDelivery` — доставка бесплатна для покупателя. СДЭК при этом работает как обычно:
  тариф считается, ПВЗ выбирается, отправление после оплаты регистрируется по тому же
  `tariffCode`. В ЮKassa уходит только стоимость товаров, а счёт от СДЭК придёт мастерской.

Как это устроено:

- Оба флага действуют на весь заказ, если помечен хотя бы один его товар: платёж и посылка
  у заказа одни на всех. Читаются только из Payload — на чекауте из уже прочитанных документов
  товара, в расчёте доставки через `hasFreeDelivery` (`src/entities/product`); из браузера
  такое принимать нельзя, это деньги.
- Бесплатная доставка — это `cost: 0` в заказе, отдельного флага нет: `delivery.tariffCode`
  остаётся настоящим, поэтому отправление регистрируется как обычно. Ноль показывается словом
  «Бесплатно» — `formatDeliveryCost` в `src/shared/lib/format.ts` (чекаут, профиль, письма).
- Магазин ЮKassa запоминается в заказе (`orders.testPayment`, readOnly): вебхук и сверка в
  профиле перезапрашивают платёж теми же ключами, которыми он создан. Поэтому вебхук сначала
  ищет заказ по `paymentId` из тела и только потом идёт в ЮKassa — тестовый магазин про боевой
  платёж ничего не знает.

## Команды

```bash
npm install        # первый запуск
cp .env.example .env.local   # заполнить DATABASE_URL и SMTP_* — см. описания в файле
npm run auth:migrate  # один раз после того, как DATABASE_URL указывает на реальный Postgres — создаёт таблицы Better Auth
npm run dev        # http://localhost:3000
npm run build      # проверка типов + сборка
npm run test:e2e   # E2E-прогон (нужен запущенный Postgres, см. ниже)
```

Без `DATABASE_URL` сайт работает, но `/auth` не сможет войти (Better Auth падает на подключении к БД). Без `SMS_RU_API_ID` вход не работает совсем — ни локально, ни на проде: номер, на который звонить, выдаёт SMS.ru. `BETTER_AUTH_SECRET` уже сгенерирован в `.env.local` — трогать не нужно.

`npm run auth:migrate` после смены плагина auth уже прогнан — он добавил в таблицу `user` колонки `phoneNumber`/`phoneNumberVerified`. Повторять нужно только на новой БД.

CLI Payload (`payload migrate`, `generate:types`, `run`) раньше падал с `ERR_REQUIRE_ASYNC_MODULE` — это **починено** файлом `payload/package.json` с единственным полем `{"type":"module"}`. Причина была не в лексикале как таковом: в корневом `package.json` нет `"type": "module"`, поэтому tsx грузил `payload.config.ts` как CJS и делал `require()` на `@payloadcms/richtext-lexical`, а там top-level await, который Node из CJS подключить не даёт. Отдельный `package.json` переводит папку в ESM. **Не удалять этот файл** — без него ломаются все команды `payload:*`.

Схема и каталог — один скрипт `payload/seed.ts` с режимом в переменной `SEED`. Схему (drizzle push) он синхронизирует всегда, каталог — только если `SEED` задан:

```bash
npm run payload:push               # только схема БД под текущие коллекции
SEED=sync npm run payload:push     # + привести каталог к payload/seed.ts, не трогая остатки и фото
SEED=photos npm run payload:push   # + проставить фото товарам без media
npm run payload:seed               # ⚠️ полный пересид: удаляет ВСЕ products и media (то же, что SEED=1)
```

На проде то же самое делает `npm run deploy:migrate` в контейнере `migrate` — он добавляет к этому `better-auth migrate` и `NODE_ENV=development` (без него drizzle push не отработает). Отдельного shell-скрипта под это нет и не нужно: вся логика режимов живёт в самом `seed.ts`.

⚠️ Побочный эффект локального `next dev`: Payload генерирует `payload/payload-types.ts` (файл в `.gitignore`). В CI его нет, локально он есть — следите, чтобы `npm run build` был зелёным именно с ним.

## Тесты

E2E на **Playwright** — единственный вид тестов в проекте. Юнит-тестов нет сознательно: проверять надо не отдельные функции, а что покупка проходит целиком.

```bash
docker compose up -d db   # Postgres на 5433 — прогон работает с настоящей базой
npm run test:e2e          # весь набор
npm run test:e2e:ui       # интерактивный режим Playwright
npm run test:e2e:report   # отчёт последнего прогона
```

Как устроено (`e2e/`):

- `scripts/serve.mjs` — поднимает прогон: пересоздаёт базу `omnia_e2e`, накатывает таблицы Better Auth, запускает `next dev` со своим `distDir` (`.next-e2e`, иначе Next не даёт запустить второй dev-сервер рядом с рабочим), ждёт drizzle push и заводит каталог через настоящий REST Payload под админом. Готовность объявляется отдельным портом — Playwright ждёт именно его, чтобы тесты не начались на пустом каталоге. Схему здесь накатывает сам `next dev` (push срабатывает при подключении, раз `NODE_ENV !== "production"`), поэтому отдельный шаг `payload:push`, как в деплое, прогону не нужен.
- `mocks/server.mjs` — настоящий HTTP-сервер вместо SMS.ru, ЮKassa и СДЭК плюс SMTP-приёмник писем. Приложение ходит в него по сети теми же запросами, что и в бой, — подменены только базовые адреса (`SMS_RU_API_URL`, `YOOKASSA_API_URL`, `CDEK_API_URL`). Внутри процесса приложения не мокается ничего. Боевые песочницы не годятся: звонок в SMS.ru в пайплайне некому совершить и он платный, а форму ЮKassa некому нажать.
- `fixtures.ts` — шаги покупателя (корзина, чекаут, подтверждение телефона, выбор ПВЗ), доступ к заглушкам и чтение результата через REST Payload. `waitForAppReady` ждёт гидратацию: до неё ввод в форму просто теряется.
- `tests/` — витрина, корзина, вход по звонку, оформление, оплата, защита денег и данных.

Что важно помнить при правках:

- Прогон однопоточный (`workers: 1`): тесты делят базу и заглушки, а «не продать один инструмент дважды» без общего остатка не проверить.
- Каждый тест ходит со своего `X-Forwarded-For` — иначе весь прогон для лимита попыток звонка выглядит одним человеком (10 в час на IP).
- После теста незакрытые заказы отменяются, а остатки возвращаются (`Shop.resetState`): `pending` держит резерв товара на полчаса.
- Подмену данных тесты делают правкой тела Server Action на лету (`page.route`) — так же, как это сделал бы злоумышленник.

В пайплайне: `.github/workflows/e2e.yml` — переиспользуемый прогон с Postgres в сервисах; вызывается из `ci.yml` на пул-реквестах и из `deploy.yml` перед сборкой образа, так что красные тесты останавливают выкатку на прод.

## Конвенции

- Язык интерфейса и коммуникации — русский. Валюта — ₽ через `formatPrice` (src/shared/lib/format.ts).
- Server Components по умолчанию; `"use client"` — только там, где есть состояние/события.
- Не выдумывать характеристики инструментов: `notesCount` реалистично 8–22 (для строёв с нижними нотами — «10+3» и т.п. из имени аудиофайла — это сумма верхних и нижних, см. `payload/seed.ts`). Диаметр (53 см + 3 см окантовка), вес (3800 г) и материал (нержавеющая сталь Ember) одинаковы для всех хангов — захардкожены как константы в `src/entities/product/model/constants.ts`, не поля Payload.
- Доступность: aria-label на иконочных кнопках, `prefers-reduced-motion` для анимаций, фокус-стили не убирать.
